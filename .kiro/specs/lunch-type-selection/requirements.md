# 要件定義書

## はじめに

天王洲アイルランチAIアプリケーションに、ランチの種類（店舗またはキッチンカー）を選択できる機能を追加します。これにより、ユーザーは固定店舗での食事か、キッチンカーでの食事かを選択でき、より柔軟なランチ提案を受けられるようになります。

キッチンカーの情報はCSVファイルから読み込まれ、リクエストされた曜日に基づいてフィルタリングされます。キッチンカーの推薦では、Google Search Groundingは使用せず、CSVに記載された情報のみを使用します。

## 用語集

- **システム**: 天王洲アイルランチAIアプリケーション
- **ユーザー**: アプリケーションを利用してランチの提案を受ける人
- **ランチタイプ**: 店舗またはキッチンカーの選択肢
- **店舗**: 固定の場所で営業しているレストラン
- **キッチンカー**: 移動式の飲食店
- **推薦エンジン**: Gemini AIを使用したレストラン提案システム
- **UI**: ユーザーインターフェース（フロントエンド）
- **API**: バックエンドのレコメンデーションエンドポイント
- **CSVファイル**: キッチンカーの情報を格納するデータファイル
- **曜日フィルタリング**: リクエストされた曜日に営業しているキッチンカーのみを抽出する処理
- **プロンプト生成**: AIに送信するメッセージを構築する処理
- **Google Search Grounding**: Googleの検索結果を使用してAIの回答を補強する機能

## 要件

### 要件1

**ユーザーストーリー:** ユーザーとして、店舗とキッチンカーのどちらでランチを食べたいかを選択したい。なぜなら、その日の気分や状況に応じて異なるタイプのランチを楽しみたいからです。

#### 受入基準

1. WHEN ユーザーがランチタイプ選択UIを表示する THEN システムは「店舗」と「キッチンカー」の2つの選択肢を表示しなければならない
2. WHEN ユーザーがページを初めて訪問する THEN システムは「店舗」をデフォルト値として選択しなければならない
3. WHEN ユーザーがランチタイプを選択する THEN システムは選択された項目を視覚的に強調表示しなければならない
4. WHEN ユーザーが「店舗」を選択する THEN システムは選択状態を保持しなければならない
5. WHEN ユーザーが「キッチンカー」を選択する THEN システムは選択状態を保持しなければならない

### 要件2

**ユーザーストーリー:** ユーザーとして、選択したランチタイプに基づいた提案を受けたい。なぜなら、店舗とキッチンカーでは異なる選択肢があるからです。

#### 受入基準

1. WHEN ユーザーが「店舗」を選択して推薦をリクエストする THEN システムは店舗リストから1つをランダムに選択しなければならない
2. WHEN ユーザーが「キッチンカー」を選択して推薦をリクエストする THEN システムはキッチンカーリストから1つをランダムに選択しなければならない
3. WHEN 推薦エンジンがレストランを選択する THEN システムは選択されたランチタイプに対応するリストのみを使用しなければならない
4. WHEN APIがリクエストを受信する THEN システムはランチタイプパラメータを含めなければならない
5. WHEN APIがレスポンスを返す THEN システムは選択されたランチタイプに適合する推薦を返さなければならない

### 要件3

**ユーザーストーリー:** 開発者として、店舗とキッチンカーのデータを別々に管理したい。なぜなら、それぞれ異なる特性を持ち、独立して更新する必要があるからです。

#### 受入基準

1. WHEN システムが初期化される THEN システムは店舗リストを定数として定義しなければならない
2. WHEN システムがキッチンカーデータを必要とする THEN システムはCSVファイルから読み込まなければならない
3. WHEN 新しい店舗が追加される THEN システムは店舗リストのみを更新しなければならない
4. WHEN 新しいキッチンカーが追加される THEN システムはCSVファイルのみを更新しなければならない
5. WHEN システムがレストランデータにアクセスする THEN システムは型安全性を保証しなければならない
6. WHEN システムがランチタイプを処理する THEN システムは「store」と「food-truck」の2つの値のみを許可しなければならない

### 要件7

**ユーザーストーリー:** ユーザーとして、その日営業しているキッチンカーのみを提案してほしい。なぜなら、営業していないキッチンカーを提案されても利用できないからです。

#### 受入基準

1. WHEN ユーザーがキッチンカーを選択して推薦をリクエストする THEN システムはリクエストに曜日情報を含めなければならない
2. WHEN APIがキッチンカーの推薦リクエストを受信する THEN システムは指定された曜日に営業しているキッチンカーのみを抽出しなければならない
3. WHEN CSVファイルから曜日でフィルタリングする THEN システムは該当する曜日のレコードのみを返さなければならない
4. WHEN フィルタリング後のキッチンカーリストが空である THEN システムは適切なエラーメッセージを返さなければならない
5. WHEN キッチンカーを選択する THEN システムはフィルタリング済みのリストからランダムに1つを選択しなければならない

### 要件8

**ユーザーストーリー:** 開発者として、店舗とキッチンカーで異なるAIプロンプトを使用したい。なぜなら、キッチンカーではGoogle Search Groundingが不要であり、CSVの情報のみを使用するからです。

#### 受入基準

1. WHEN システムがAIプロンプトを生成する THEN システムはランチタイプに基づいて異なるプロンプト生成関数を呼び出さなければならない
2. WHEN 店舗の推薦を生成する THEN システムはGoogle Search Groundingを有効にしなければならない
3. WHEN キッチンカーの推薦を生成する THEN システムはGoogle Search Groundingを無効にしなければならない
4. WHEN キッチンカーのプロンプトを生成する THEN システムはCSVから取得した詳細情報（ジャンル、メニュー、営業時間、会場）を含めなければならない
5. WHEN プロンプト生成ロジックを変更する THEN システムは該当するランチタイプのプロンプト生成関数のみを変更すればよい状態でなければならない

### 要件9

**ユーザーストーリー:** ユーザーとして、キッチンカーの推薦結果にもマップリンクを表示してほしい。なぜなら、会場の場所を地図で確認したいからです。

#### 受入基準

1. WHEN キッチンカーの推薦結果を生成する THEN システムは会場名に基づいたGoogle Mapsの検索リンクを生成しなければならない
2. WHEN 店舗の推薦結果を生成する THEN システムは店舗名に基づいたGoogle Mapsの検索リンクを含めなければならない
3. WHEN 推薦結果を表示する THEN システムはマップリンクをクリック可能なリンクとして表示しなければならない
4. WHEN キッチンカーの推薦結果を表示する THEN システムは会場情報とマップリンクの両方を表示しなければならない
5. WHEN マップリンクを生成する THEN システムは適切なURLエンコーディングを適用しなければならない

### 要件4

**ユーザーストーリー:** ユーザーとして、ランチタイプの選択が他の入力項目と一貫したUIで表示されることを期待する。なぜなら、統一されたユーザー体験が重要だからです。

#### 受入基準

1. WHEN ランチタイプ選択UIが表示される THEN システムは気分選択や天気選択と同じデザインパターンを使用しなければならない
2. WHEN ユーザーがランチタイプボタンにホバーする THEN システムは視覚的なフィードバックを提供しなければならない
3. WHEN ランチタイプが選択される THEN システムは選択状態を青色のボーダーとスケールアップで示さなければならない
4. WHEN ランチタイプ選択が表示される THEN システムは適切なアイコン（絵文字）を各選択肢に表示しなければならない
5. WHEN モバイルデバイスで表示される THEN システムはランチタイプ選択をレスポンシブに表示しなければならない

### 要件5

**ユーザーストーリー:** ユーザーとして、推薦結果にランチタイプの情報が含まれることを期待する。なぜなら、自分が選択したタイプの店を提案されたことを確認したいからです。

#### 受入基準

1. WHEN 推薦結果が表示される THEN システムはランチタイプ（店舗またはキッチンカー）を結果に含めなければならない
2. WHEN 推薦モーダルが表示される THEN システムはランチタイプを視覚的に識別可能な形で表示しなければならない
3. WHEN ユーザーが保存された結果を閲覧する THEN システムはランチタイプ情報を保持しなければならない
4. WHEN Cookieに結果を保存する THEN システムはランチタイプ情報を含めなければならない
5. WHEN Cookieから結果を読み込む THEN システムはランチタイプ情報を復元しなければならない

### 要件6

**ユーザーストーリー:** ユーザーとして、フォームをリセットしたときにランチタイプもデフォルト値に戻ることを期待する。なぜなら、新しい検索を始めるときは初期状態から始めたいからです。

#### 受入基準

1. WHEN ユーザーがリセットボタンをクリックする THEN システムはランチタイプを「店舗」にリセットしなければならない
2. WHEN リセットが実行される THEN システムは名前、気分、天気、ランチタイプのすべてをクリアまたはデフォルト値に戻さなければならない
3. WHEN リセット後 THEN システムは推薦結果とエラーメッセージをクリアしなければならない
4. WHEN リセットが完了する THEN システムはUIを初期状態に戻さなければならない
5. WHEN リセットボタンが表示される THEN システムは何らかの入力がある場合のみリセットボタンを表示しなければならない
